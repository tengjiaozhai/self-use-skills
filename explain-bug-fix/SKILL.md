# Explain Bug Fix

用 SCQA 围绕读者的问题组织讲解：**正常机制 → 异常与影响 → 核心疑问 → 排查证据 → 新旧代码与修复原理 → 验证及变式练习**。吸收 STAR 对目标、行动和结果的要求，分别融入期望行为、排查修复和验证；输出时沿一条主线展开。

## 获取本次材料

先用当前对话、指定仓库、issue/PR、版本差异和已有验证结果补齐以下信息，能自行定位的无需用户重新整理：

- **场景**：一个具体输入或操作、起始状态、实际结果、原本期待的结果，以及有证据支持的影响。
- **旧、新基线**：用户指定的 commit/分支/PR、未提交 diff 或两份文件；记录各自版本，读取相关函数与实际调用方。HEAD 可能已经包含修复，不能固定当作旧版本。
- **验证**：复现步骤、测试输出、日志或运行记录；保留真实依赖与替身的范围，以及未运行的部分。

缺少旧版本时先检索明确相关的差异或提交；仍找不到，就说明只能解释当前行为。只有答案会实质改变因果结论且无法自行查证时，才询问缺失的版本、输入或运行条件。

本 Skill 默认做只读讲解。用户同时要求修复时，先完成授权范围内的诊断与修改，保留前后证据，再解释结果；Skill 本身不扩展修改或发布权限。

## 围绕场景展开

先用一句话说明当前结论与证据状态，再按以下顺序展开。SCQA 用于组织解释；根因尚未确定时，保留待验证的问题，不为完整叙事补造结论。

### 1. 正常机制：Situation

交代用户想完成什么，沿哪个实际入口执行，关键状态应由谁产生、保存和读取。只引入理解本次故障需要的机制。

把修复目标写成可检查的行为要求，例如“同一任务重试成功后，回复与可恢复状态一起保存；无关任务成功不能覆盖原失败”。目标用于判断方案是否有效，不以“加一个参数”代替。

**完成条件**：读者知道正确行为是什么，以及判断正确与否的条件。

### 2. 异常与影响：Complication

对照期望行为描述实际观察：什么输入、在哪一轮或哪一步、出现了什么偏差，影响了哪项操作。截图可以证明页面现象，不能单独证明根因；影响范围未知时直说，不自行扩大为数据丢失、重复扣费等后果。

**完成条件**：异常与正常机制之间的矛盾清楚，已观察的影响与推测分开。

### 3. 核心疑问：Question

把“怎么修”收紧为能靠代码或运行证据回答的问题。例如“令牌已生成，为什么下一轮没有？是未保存、未恢复，还是恢复后漏填参数？”若概念混淆阻碍判断，先解释它们的职责差别，例如工具实现存在与本轮注册可调用。

**完成条件**：问题指向待解释的分支或状态断点，后续证据能支持或排除相应解释。

### 4. 排查证据：从现象回到旧代码

沿真实执行路径找到决定错误行为的条件或状态流：

```text
具体输入／起始状态 → 旧判断或操作 → 实际走入的分支 → 下游错误结果
```

用少量关键代码、触发值和状态记录连接这条链。说明哪些证据改变了判断，哪些解释已被排除，哪些仍待验证；只把实际调查过的猜想写成排查经过，不能把事后知道的根因包装成当时已经验证的过程。读到足以解释分支为止。

**完成条件**：能指出具体输入下哪条旧逻辑成立，如何导致用户看到的结果；其中未复现的连接明确标为推断。

### 5. 修复答案：Answer 与新旧代码对照

SCQA 的 A 是 Answer，先回答核心疑问，再说明真正改变因果链的最小充分修改：

- 旧条件／操作是什么，新条件／操作是什么？
- 在相同输入与前提下，为什么现在走入另一条分支或保存了不同状态？
- 哪些下游代码没有改，却因为上游输入或状态修正而恢复工作？

用相同触发条件做前后对照。若新流程需要补上下文、改变输入或配置，单独写明这些差异；例如“原错误输入现在被拒绝”与“补全对象后正确执行”是两个结果，不能合并成一句“修后同输入必定成功”。

修复过程包含多个问题时，分别标明**原有问题被暴露**、**修改引入的回归**或**尚未证实的疑点**。只有前后证据支持，才说某次修改引入了新问题；每个实际问题仍按旧逻辑、改动、结果讲清楚。

**完成条件**：每个解释中的改动都对应一个失效条件；“重构了一下”“加了校验”之类描述已经展开为可检查的机制。

### 6. 验证结果与学习迁移

把结论分别落到源码、复现、测试或目标运行环境。静态阅读只证明存在这条代码路径；隔离测试、固定模型、真实模型、真实用户环境分别说明，不用其中一项替代另一项。

若只是重述已有验证，标明其版本或时间，不说本轮重新验证。没有验证的修复可以解释设计意图，但要保留“是否解决实际故障尚未证实”。指出本次修复仍然依赖的条件，而不是追加假想风险清单。

用户希望学习或深入复盘场景时，在讲解末尾给一道变式练习：只改变一个关键条件，让读者预测分支、状态或结果，并附参考答案和推导依据。可给出现有代码的断点、待观察变量和预期值；无需为普通讲解另建脚本或等待用户作答。未执行的练习预期标为推导，不能计入验证结果。

**完成条件**：读者能区分已证实的结果、代码推断和剩余边界；学习场景还应能解释改变一个条件后为什么会走另一条分支。

## 表达与交付

以上是内容顺序，不要求每次输出六个标题。简单问题可压缩为一段；深入学习时展开证据和代码，并使用自然标题。篇幅主要用于解释关键条件与状态如何变化。

代码用实际语言的代码块，并附已核对的文件／函数定位；能提供准确行号时再给行号。真实摘录与教学简化示意要明确区分，不能把简化代码声称为仓库原文。表格适合比较概念或相同输入的前后结果，短箭头链适合展示跨层传播。

用户要求学习具体场景，或存在路由、重试、状态跨轮等概念混淆时，参考 [场景讲解与变式练习](references/examples.md) 校准粒度。样例仅示范表达方式，不提供其他项目的根因或代码事实。

交付前检查：读者能否复述正常行为、异常影响、排查依据，以及“什么输入 → 旧条件 → 错误结果；改了哪个条件 → 为什么恢复”？学习场景再检查练习能否用这条因果链解释。只有改动清单或结论、缺少中间联系时，继续补足。
