# 因果讲解样例

以下来自两类真实故障的表达结构，代码是**教学简化示意**，省略项目路径与非关键逻辑。实际任务须重新读取自己的版本、函数和证据，不能照搬案例结论。

## 样例一：关键词命中为什么影响工具可见性

**现象**：用户说“确认提交”，主智能体回答没有管理工具，仓库里却已经实现了管理子智能体。

先区分：意图是本轮任务的分类，工具是模型本轮能调用的能力。子智能体代码存在，不等于它已经注册进本轮工具列表。

旧流程把确认句改写成“提交综合最佳方案（……酒店 H2……）”，丢失了“差旅申请”对象；旧规则又允许仅凭酒店名词命中酒店搜索：

```python
for rule in rules:
    if rule.matches(text):
        return rule.intent
```

本次输入含“酒店”，却不满足申请动作所需的业务对象；分类因此走错。下游按意图装配工具，管理能力未开放，所以主模型确实看不到管理工具。

修复分两部分：确认对象不明确时先从历史补全；规则命中必须解释当前动作，不能用后面的酒店明细代替“提交”。已有的工具装配条件继续生效，无须把意图名称直接替换成工具名称。

```text
明确提交差旅申请 → 命中申请意图 → 管理工具注册 → 模型有机会委派
```

前后对照要拆开看：错误改写修后被拒绝猜测；补全申请对象后才命中申请；真正查询酒店仍是酒店搜索。工具已可见，也不等于模型每次一定调用。

## 样例二：重试成功为什么仍然丢失跨轮状态

**现象**：页面已经显示待确认摘要，下一用户轮次的确认令牌却为空。

已取得的证据是：同轮首次委派失败，重试成功生成摘要，但这一轮没有保存助手消息和新的子智能体状态。旧代码只要找到任何失败记录就提前结束：

```python
if any(call.status == "failed" for call in calls):
    return error
save_reply_and_state()
```

调用记录虽然是“失败、成功”，前一次失败仍会挡住保存。正文已经流到页面，但令牌没有进入下一轮可恢复的状态，因此不能解释为“令牌校验失败后模型主动丢弃”。

不能简单取所有调用的最后一个结果：另一个任务的成功也可能掩盖原失败。修复先显式关联重试所属任务，再按同一任务的最终结果判定：

```text
任务 A：失败 → 显式重试 A 成功 → A 已恢复，可保存成功状态
任务 A：失败；任务 B：成功     → A 仍失败，不能宣称整轮成功
```

用于关联委派的 `retry_of` 与后续提交所需的 `confirmation_token` 各有职责。前者复用本轮委派参数，不能回收失败执行的半完成状态，也不代表业务确认。

随后把可见回复与所依赖的运行状态一起提交；前端以保存确认事件判完成，失败正文明确失效。这些改动解决了不同位置的不一致，不能只列成“改了重试、数据库、页面”三个文件清单。

验证仍需分层：固定模型和隔离存储可以证明该状态链路，不能证明真实模型永不漏填参数；聊天记录回滚也不代表此前业务操作已撤销。
