# 场景讲解与变式练习

以下来自两类真实故障的表达结构，代码是**教学简化示意**，省略项目路径与非关键逻辑。表格与练习中的结果用于说明分支含义，不代表本 Skill 在目标环境重新执行了验证。实际任务须读取自己的版本、函数和证据，不能照搬案例结论或把推导写成测试通过。

每个样例沿一条 SCQA 主线展开，排查证据和验证各自写清。标题服务于读者，不必在每个回答中展示字母标签。

## 样例一：关键词命中为什么影响工具可见性

### 正常机制

历史已经明确讨论差旅申请时，用户说“确认提交”，系统应补全提交对象、识别申请意图，再向主模型开放管理工具。对象仍不明确时，应保留歧义。

意图是本轮任务的分类，工具是模型本轮能调用的能力。子智能体代码存在，不等于它已经注册进本轮工具列表。

### 异常与影响

主智能体回答没有管理工具，仓库里却已经实现了管理子智能体。当前请求无法沿管理工具继续处理；仅凭这句话，还不能判断工具实现缺失。

### 核心疑问

本轮管理工具究竟没有实现，还是没有被注册？如果没有注册，哪一步的输入导致装配条件不成立？

### 排查证据与旧代码

查看实际改写文本、意图结果和工具列表，比只搜索管理子智能体类名更接近这个问题。案例中的改写是“提交综合最佳方案（……酒店 H2……）”，丢失了“差旅申请”对象；旧规则允许仅凭酒店名词命中酒店搜索：

```python
for rule in rules:
    if rule.matches(text):
        return rule.intent
```

本次输入含“酒店”，却不满足申请动作所需的业务对象；分类因此走错。下游按意图装配工具，管理能力未开放，所以主模型确实看不到管理工具。这条链能解释本轮工具不可见，不代表工具实现被删除。

### 修复答案与新路径

修复先让确认对象从明确的历史中补全，再要求规则命中解释当前动作，防止后面的酒店明细代替“提交”。已有的工具装配条件继续生效，无须把意图名称直接替换成工具名称。

```text
明确提交差旅申请 → 命中申请意图 → 管理工具注册 → 模型有机会委派
```

### 验证与边界

前后对照要分别检查以下输入，不能把“修正了输入”混作“同一输入修后直接成功”：

| 输入条件 | 旧逻辑 | 新逻辑应有的结果 |
| --- | --- | --- |
| 提交方案，含酒店明细，申请对象缺失 | 酒店关键词抢先命中 | 保留歧义，不猜成申请 |
| 明确提交差旅申请，含酒店明细 | 申请与背景酒店可能冲突 | 申请意图成立，开放管理工具 |
| 确实请求查询上海酒店 | 酒店搜索 | 仍是酒店搜索 |

这些分支需要对应版本的规则验证。检查工具列表可以证明能力可见，不能证明真实模型每次一定委派。

### 变式练习

**题目**：只改变历史条件：历史没有说明提交对象，用户仍说“确认提交”，上一份展示内容里出现了酒店。能直接开放管理工具吗？应观察什么？

**参考答案（按上述机制推导）**：不能仅凭酒店明细推断申请对象，也不能把确认自动升级为提交。应观察历史是否存在明确待确认对象、改写是否保留业务动作与对象、意图是否仍有歧义。缺少对象时应澄清；工具装配跟随已确定的意图。

## 样例二：重试成功为什么仍然丢失跨轮状态

### 正常机制

工具在第一轮生成摘要和令牌，令牌随子智能体状态一起保存；下一轮恢复状态后，模型才能从上下文读取并填写令牌。正确行为要求回复与所依赖的状态一起保存，同一任务的成功重试能恢复该任务，无关任务成功不能覆盖其失败。

### 异常与影响

页面已经显示待确认摘要，下一用户轮次的确认令牌却为空，提交工具再次进入生成摘要的阶段。用户确认未能推进到提交，页面展示与可恢复状态出现矛盾。

### 核心疑问

令牌没有生成、没有保存、没有恢复，还是恢复后模型漏填？页面出现摘要能证明到哪一步？

### 排查证据与旧代码

本案例的关键证据是：同轮首次委派失败，重试成功生成摘要，但这一轮没有保存助手消息和新的子智能体状态。它把断点收紧到了保存之前；其他场景要重新核对这些记录，不能仅凭参数为空套用此根因。

旧代码只要找到任何失败记录就提前结束：

```python
if any(call.status == "failed" for call in calls):
    return error
save_reply_and_state()
```

调用记录虽然是“失败、成功”，前一次失败仍会挡住保存。正文已经流到页面，但令牌没有进入下一轮可恢复的状态，因此不能解释为“令牌校验失败后模型主动丢弃”。

### 修复答案与新路径

不能简单取所有调用的最后一个结果：另一个任务的成功也可能掩盖原失败。修复先显式关联重试所属任务，再按同一任务的最终结果判定：

```python
final_by_task = {}
for call in calls:
    final_by_task[(call.tool_name, call.task_id)] = call
if any(call.status == "failed" for call in final_by_task.values()):
    return error
save_reply_and_state_atomically()
```

这段示意以服务端已经校验重试关联、调用记录按实际顺序排列为前提。`retry_of` 关联本轮委派并复用原始参数；后续提交所需的 `confirmation_token` 用于业务确认。二者职责不同，前者不能回收失败执行的半完成状态。

随后把可见回复与所依赖的运行状态一起提交；前端以保存确认事件判完成，失败正文明确失效。这些改动解决了不同位置的不一致，不能只列成“改了重试、数据库、页面”三个文件清单。

### 验证与边界

| 条件 | 应核对的结果 |
| --- | --- |
| 仅任务 A，失败后显式重试成功 | A 的最终结果成功，可进入回复与状态保存；提交成功后两者都可恢复 |
| A 失败，另一个任务 B 成功 | A 仍失败，不能判整轮成功 |
| A 重试成功，但状态保存失败 | 回复与状态均不能作为本轮成功结果提交；流式摘要标为无效 |

验证仍需分层：固定模型和隔离存储可以证明该状态链路，不能证明真实模型永不漏填参数；聊天记录回滚也不代表此前业务操作已撤销。

### 变式练习

**题目**：A 失败后，出现一条内容相似的成功调用，但没有经过重试关联校验。能把它当作 A 的恢复吗？应在哪个分支或变量上核对？

**参考答案（按上述机制推导）**：不能凭相似文本或先后顺序认定同一任务。应检查服务端是否接受了 `retry_of`、成功调用是否沿用 A 的 `task_id`，再观察最终判定和保存分支。若它属于独立任务，A 仍失败；若确实是经校验的 A 重试，A 的最终结果才可更新为成功。即使最终结果成功，也要继续核对原子保存是否完成。
